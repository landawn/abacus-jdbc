# Performance and memory review — 2026-10-27

Four reviewers inspected all **101 Java source files, comprising 116,248 physical lines**, under `src/main/java`. Every implementation and declaration was reviewed, including nested types, interface defaults, initializers, and cleanup paths. Relevant Javadoc contracts were checked; comments, whitespace, and the archived `SqlExecutor` implementation are not counted as executable code. Baseline: `24030f750e6f5ac6f2b5e5f21f854eb7c58d4d35`. No production source or existing test was changed by this review.

After follow-up assessment, the review identifies **eight findings: one P1, four P2, and three P3**. Premature result advancement can discard MySQL rows (P1). Join-enrichment streams can exhaust the connection pool (P2 generally, P1 for affected workloads). Other findings concern retained row values, unbounded per-dialect plans, redundant binding preparation, metadata fallback execution, and lock retry traffic. P2/P3 priorities apply to the workloads described below; they are not claims that all applications experience a bottleneck. F5 is the first performance optimization to implement after the correctness fix; finding numbers do not represent implementation order.

This document records baseline findings and source locations, which may shift after edits. Subsequent implementation and its validation are recorded in [implementation notes](performance-memory-implementation-2026-10-27.md).

## F1 — Defer multiple-result advancement until after extraction

Location: [JdbcUtil.java:9565](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/JdbcUtil.java:9565), specifically lines 9565–9568.

`iterateAllResultSets.next()` removes the current ResultSet from its holder, invokes `getMoreResults(KEEP_CURRENT_RESULT)`, then returns the current ResultSet. Connector/J 26.7.0 reports support for multiple open results, but its actual `StatementImpl.getMoreResults(int)` drains any current streaming rows before advancing. Consequently the extractor receives an exhausted cursor when a forward-only, read-only statement uses `fetchSize = Integer.MIN_VALUE`. This streaming configuration is explicitly supported by the query API. One SELECT consumed through a multiple-result API is sufficient to trigger the issue.

Affected callers include `AbstractQuery.queryAllResultSets` at 6310–6315, `streamAllResultSets` at 8754–8757, two/three-result and list-all-result overloads, `CallableQuery` multiple-result/OUT-parameter operations, and the raw `JdbcUtil.streamAllResultSets` helpers. Advancing eagerly also delays application processing while the driver performs that drain.

**Evidence:** the probe invoked the pinned driver's real `StatementImpl.getMoreResults`, with normal open-resource tracking and a simulated 100-row cursor. The iterator caused 101 `next()` calls before returning; the application's first `next()` returned false. Installed driver source confirms the drain at `StatementImpl.java:1696–1701` and reported multiple-result support at `DatabaseMetaData.java:1784–1786`. The network and row source were simulated; this is not a live server integration test.

**Recommended fix:** defer advancement until the next iterator demand for every driver. Preserve KEEP for results that are still open; use CLOSE for results the caller has already closed. Give the current extractor an opportunity to consume its result first. Also preserve Connector/J's discovery of trailing results when closing a partially consumed streaming cursor: its close notification precedes its normal close-time drain, so that mode needs a drain before close. Preserve update-count skipping, trailing-result cleanup, early stream close, and exception ownership. Validate both streaming and buffered MySQL results, unsupported KEEP behavior, and live MySQL streaming when available. Confidence: high.

## F2 — Avoid hidden nested connection acquisition in join streams

Location: [JoinEntityReadOps.java:467](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/dao/JoinEntityReadOps.java:467), particularly 467–471; the other join-stream overloads repeat this at 516–521 and 563–567. Unchecked variants delegate to the same behavior.

The parent query stream remains open while `.split(DEFAULT_BATCH_SIZE).onEach(...)` loads children. Outside a transaction, those child queries borrow another connection from the same source. A pool with one available connection cannot supply it because the parent stream is waiting for the child query before it can progress or close. With concurrent streams, a larger pool can reach the same condition when parent cursors occupy all connections. The API's batching limits the parent chunk size, but does not address this pool dependency.

**Evidence:** actual HikariCP 7.1.0 and H2 2.5.252, pool size one, 250 ms acquisition timeout, and 201 parents (one more than the 200-row chunk). A parent-only `limit(1)` succeeded; the joined `limit(1)` failed to acquire a connection after a reported 262 ms pool wait. A joined eager list returned all 201 rows. With pool size two, the joined stream returned its first row and child successfully. Both cases ended with zero active connections after close: this is starvation during consumption, not a demonstrated permanent connection leak. The concurrent-pool scenario follows from the same dependency; only the deterministic single-stream case was executed.

**Recommended action:** immediately document the additional connection-capacity requirement on every enrichment-stream overload, reserve capacity for child queries, and bound concurrent joined streams. A transaction-bound connection instead runs child queries on the parent's connection, where active streaming cursors may prohibit another statement; a larger pool does not solve that restriction. Any page-based iterator or server-side join strategy must be opt-in with explicit ordering and pagination semantics; do not silently change existing streams. Driver-supported buffering or materializing/closing parent results before child queries are other alternatives. Confidence: high in the dependency; default priority P2, elevated for deployments encountering starvation.

## F3 — Clear reusable scratch-row references after callbacks

Primary location: [Jdbc.java:5459](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/Jdbc.java:5459), lines 5459–5463. Related sites: typed/bi consumers at 5554–5558, 5687–5691, 5781–5785; finisher mappers at 3047–3051 and 3120–3124; extractor-backed map mappers at 4157–4171, 4321–4329, and 4401–4409.

The factories save allocation by reusing an Object array, but its last-row values remain strongly reachable after the callback or finisher returns. Applications that keep these stateful callbacks for later queries consequently keep the final row's payloads. This can happen even when the callback discards everything or a map filter rejects every entry. Closing the result set does not clear the independent scratch fields. The retention is **one row per retained callback**, not the entire query result.

**Evidence:** deterministic inspection found the same 8 MiB synthetic byte array in the surviving scratch field of a row consumer, bi-row consumer, scalar-returning finisher mapper, and rejecting map mapper. The fixture tested the same payload across four representative paths; it does not claim 32 MiB of production heap use or a measured GC leak.

**Recommended fix:** retain the reusable arrays but null their elements in a `finally` surrounding population and callback/finisher/map-copy execution, including partial-fill and failure paths. Disposable callback values must be copied if retained, as documented. Do not clear `toDisposableObjArray()` mapper buffers before returning the view: that API intentionally exposes the row. Validate success, rejection, getter/callback failure, different layouts, and retained callbacks. Confidence: high; P3 generally, elevated to P2 for long-lived callbacks with large row payloads.

## F4 — Bound per-dialect join plans as well as metadata entries

Locations: [JoinInfo.java:244](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/JoinInfo.java:244) and [JoinInfo.java:1060](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/JoinInfo.java:1060), particularly publication at 1077.

Each JoinInfo has a dialect-to-DSL map and four associated SQL-plan maps. `planDsl` builds and retains a complete plan set for every distinct SqlDialect. These maps have no capacity bound or per-dialect release. The outer metadata cache is bounded, but live DAOs/returned metadata can keep a JoinInfo alive indefinitely, allowing its inner maps to grow as custom dialects or product configurations change. Releasing a DAO metadata reference does not remove an individual dialect's plans from metadata still used elsewhere.

**Evidence:** requesting one join's select plan for 1,000 distinct accepted H2 product-version configurations yielded 1,001 entries in each of the five maps, including the preexisting plan. This synthetic cardinality demonstrates the missing bound; it is not an estimate of normal application usage. Applications using a small fixed set of dialects are unlikely to see material growth.

**Deferred design option:** if a real workload has high configuration cardinality, represent a dialect's complete plans as one immutable bundle in a bounded cache, or explicitly own/release configurations. Evict associated plan state together and keep returned plans valid; independent eviction can expose incomplete plan sets. Do not equate dialects solely by product name. Validate churn, concurrent access, dialect-specific SQL, failed construction, and retained plans before adopting this redesign. Confidence: high for the growth mechanism, but the synthetic probe does not justify eviction complexity for a small fixed dialect set; default priority P3.

## F5 — Hoist duplicate-name analysis out of JDBC batch loops

Location: [JdbcUtil.java:7617](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/JdbcUtil.java:7617), lines 7617–7620; per-row callers at 6469–6473 and 6836–6840; analysis at 7897–7933.

The named bean/map route recomputes `firstIndexesOfRepeatedNames` for every batch row, although the ParsedSql and placeholder sequence do not change. Below 32 placeholders it repeats a nested comparison scan; at 32 or more it creates and fills a HashMap, even if all names are distinct and the result is null. This work is independent of actual row values.

**Evidence:** a warmed allocation probe of the actual helper with 64 distinct names measured 26,240,000 allocated bytes over 10,000 invocations, or 2,624 B/invocation. Code tracing establishes that the batch route invokes it per row. The experiment measures this helper alone, not total binding or database cost.

**Recommended fix:** calculate the duplicate-name layout once per batch and pass its resolved/null state into the per-row binder. Keep row values, stream cursors, and getter results scoped to the row. Per-row value and type arrays remain allocated; the 2,624 B figure is not total binding allocation. No global arbitrary-SQL cache is necessary. Preserve repeated-name getter evaluation count, mixed parameter object classes, nested/null properties, missing parameters, and replay of one-shot values. Confidence: high; speedup depends on batch shape.

## F6 — Limit the remaining code-generation execution fallback

Location: [JdbcCodeGenerationUtil.java:556](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/JdbcCodeGenerationUtil.java:556), lines 556–557.

The prepared-metadata fast path is already implemented. When metadata is unavailable or inadequately typed, however, a caller-supplied SELECT executes without a row cap although generation consumes only metadata. An eager driver can evaluate or buffer a large result. Table-name overloads already use a zero-row predicate; this finding concerns unrestricted custom SQL. The fallback and `WHERE 1 = 0` workaround are documented, so this is a remaining optimization rather than an undisclosed contract change.

**Evidence:** with a proxy forcing null prepared metadata, H2 evaluated a counting function for 10,000 rows. A test-wrapper `setMaxRows(1)` reduced this to one evaluation and generated the same long field. This does not imply H2 normally needs the fallback, or that a row cap prevents scans, sorts, or aggregates on all servers.

**Recommended fix:** apply a supported one-row cap to the privately owned fallback statement, preserving compatibility if the setting is unsupported. Keep the zero-row query guidance and do not rewrite arbitrary SQL by appending predicates. Validate unknown/dynamic column types, primary keys, supported drivers, and cleanup. Confidence: high for the demonstrated path.

## F7 — Reduce database traffic from contended lock retries

Locations: [DBLock.java:624](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/DBLock.java:624), lines 624–631; delay at 672–674; connection cycle at 967–975.

Each failed acquisition attempt first deletes expired locks and then attempts INSERT, separately borrowing, preparing, executing, and closing for each statement. Convenience overloads use a documented minimum one millisecond delay. Under contention this produces repeated pool traffic, database work, and unique-constraint exception allocation. Refresh and close already reuse resources; they are not the issue reported here.

**Evidence:** a held H2 lock and 200 ms timeout produced 74 connection/preparation/update cycles at the default interval (37 delete/insert attempts), versus 14 cycles with a 25 ms interval (seven attempts). Both waited approximately 203 ms. Absolute counts are timing-dependent; two resource cycles per attempt is the code invariant.

**Recommended fix:** reuse one owned auto-commit connection within each acquisition attempt, preserving the existing release before sleep. Cleanup failures should still allow an independent insertion attempt on a fresh connection. The two SQL statements and duplicate-key exception under live contention remain; an expired-row UPDATE followed by INSERT on zero rows would not remove those exceptions. Use the existing explicit retry interval for contended workloads; opt-in backoff/jitter is a separate latency/load tradeoff. Preserve timeout clipping, interruption, expiry/stale-row recovery, and independent auto-commit behavior. Confidence: high for the mechanism; workload-dependent tuning.

## F8 — Reuse a query-local bean binding plan

Location: [NamedQuery.java:4439](C:/Users/haiyangl/Landawn/abacus-jdbc/src/main/java/com/landawn/abacus/jdbc/NamedQuery.java:4439), lines 4439–4445; existing optimized batch path at 4859–4884.

Repeated `setParameters(bean)` on the same query allocates a PropInfo array and resolves all placeholder properties each time; nested names allocate another array of property paths. The bulk add-batch method already performs this preparation once outside its loop.

**Evidence:** after warm-up, three 250,000-row measurements gave 48 B/bind for eight direct String properties and 96 B/bind for eight nested properties. The existing bulk binding route measured effectively zero per-row plan allocation against the same no-op statement. These are plan-array allocations, not JDBC throughput measurements.

**Recommended fix:** keep a single last-runtime-class binding plan on the query, rebuilding when the class changes. Cache metadata only, not entities, property values, or stream suppliers; avoid an unbounded class map. Preserve nested nulls, repeated getter semantics, mixed types, and failure handling. Confidence: high in allocation evidence; P3 because round trips often dominate and the batch API already provides the optimized route.

## Workload-dependent options and deliberate constraints

These are not additional confirmed defects:

- **CSV framing:** `DataTransferUtil.java:2350–2357` performs scalar BufferedReader calls. The probe counted 120,007 calls for 120,006 characters and 10,001 records. The input is already buffered; these are not OS reads. Benchmark a reusable char buffer before accepting parser complexity. Multiline quoting, CRLF, BOM, custom parsers, and reader ownership must remain intact. This carries forward the previously deferred O7.
- **Asynchronous backlog:** the pinned default AsyncExecutor still uses an unbounded LinkedBlockingQueue. Sustained excess submission can retain queued query/action graphs. Use existing application-owned bounded executors sized for connection capacity. A new global default/rejection policy is an API decision, previously deferred; do not silently introduce caller-runs or blocking admission.
- **Repeated stream parameters:** replay materializes one payload and creates independent cursors sharing it. Whole-payload peak allocation can be large, but there is not a payload copy for every placeholder. A supplier/spooling API needs an explicit resource/failure contract; this was deliberately retained in the earlier implementation.
- **Merged results and mapped entities:** Dataset-backed merge/mapping stages flattened rows before producing entities/maps. High join fan-out can increase peak references. A direct accumulator may help but must preserve ordering, composite/nested IDs, duplicate handling, and mapping behavior. No speed or heap reduction was measured here.
- **Batch refresh:** reads and grouping can retain all refreshed values before mutations are applied. Chunked mutation would reduce staging but change the existing all-reads-before-mutation/failure behavior; it requires an explicit opt-in contract.
- **Fetch-size and result type:** driver cursor prerequisites still determine actual buffering. Eager list/Dataset return types and deferred generated-ID/rollback state inherently retain data. Do not promise that JDBC fetch size or batch size bounds the entire operation's heap.
- **Transaction state:** completed contexts clear action logs and registry entries; Spring owners use weak holder/status references. Unresolved transaction records deliberately persist until confirmed settled to protect cache correctness. Removing that state to save memory is not safe. Retained closed wrappers/transactions still reference their delegates, but no separate accumulating leak was established from that fact alone.
