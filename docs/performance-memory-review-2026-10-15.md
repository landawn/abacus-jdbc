Performance and memory review, 2026-10-15

Follow-up: [implementation and compatibility notes](performance-memory-implementation-2026-10-15.md). The findings, measurements and source line numbers below describe the review baseline before those changes.

Four reviewers inspected all **97 Java source files (105,924 physical lines)** under `src/main/java/`, including default interface methods, nested types, static initialization, annotations, enums, and package declarations. Review baseline: commit `7c4ffbbe3420a4ef0d4ada4d071961fd71d68ce3`. All implementation and declaration lines were reviewed; Javadoc and commented historical code were distinguished from executable code. Production source and existing tests were not changed.

The review identified **seven actionable findings and fifteen additional tuning opportunities**. The most useful changes are to expose cache lifecycle cleanup, release query references from completed futures, avoid caching multiple deep copies along convenience-method chains, and avoid work proportional to entire inputs when only a batch, selected columns, or metadata is needed. Priorities below are **P2: worthwhile fixes in the specified workload**, not claims that every application is affected. No production latency or heap profile was supplied, so operation counts and retention paths are separated from throughput estimates.

Validation passed: the complete default local Maven suite reported **5,915 tests, 0 failures, 0 errors, 36 skipped**. A separate full production compilation passed with JDK 21.0.11. Focused probes used freshly compiled classes, counting JDBC/collection implementations, reference-path and GC checks, and in-memory H2. The suite and probes used installed dependencies; no external database was required. The Windows sandbox initially blocked Java classpath access and Maven used an empty sandbox-user repository. Automatically approved local executions resolved those environment restrictions; the successful results below supersede those failed attempts.

**F1. Expose the lifecycle of publicly created pooled DAO caches.**

Locations: [Jdbc.java:7859](../src/main/java/com/landawn/abacus/jdbc/Jdbc.java#L7859), [clear and close:8013](../src/main/java/com/landawn/abacus/jdbc/Jdbc.java#L8013), and the public factory at line 7666.

`Jdbc.DaoCache.create(...)` and the public `DefaultDaoCache` constructor allocate a `KeyedObjectPool`. In the actual `abacus-common` 8.1.0 dependency, each pool registers a JVM shutdown hook, and positive eviction delays also schedule a periodic task. `clear()` removes entries but leaves those resources active. The already implemented `close()` is package-private; neither the cache interface nor implementation is `AutoCloseable`.

Applications that repeatedly create and discard these caches retain backing pools until JVM exit. The hook is a retained `Thread` object, not a running worker per cache. This issue exists independently of the documented permanent DAO-proxy cache. Four directly created caches, including two with eviction disabled, remained reachable after `clear()` and loss of caller references. After internal lifecycle cleanup, all four backing pools became collectible.

Make the existing `DefaultDaoCache.close()` public and implement `AutoCloseable`. Consider a compatible lifecycle method on `DaoCache` for factory callers. Document ownership so callers do not close caches still shared by live DAOs. Keep `clear()` reusable. Verify close idempotence, scheduler/hook cleanup, normal cache operations before close, and explicitly defined behavior after close. Confidence: high.

**F2. Remove the permanent enclosing-query reference from completed asynchronous tasks.**

Location: [AbstractQuery.java:11292](../src/main/java/com/landawn/abacus/jdbc/AbstractQuery.java#L11292), especially `done()` at lines 11312-11327; the final statement field is at line 235.

The anonymous `FutureTask` calls an enclosing-query cleanup method from `done()`. Its generated `this$0` field therefore keeps the query reachable through `ContinuableFuture.future`, even after `FutureTask` clears its callable. Retaining a successful scalar or void future consequently retains the closed statement and any remaining query/driver state.

The probe completed and closed eight queries, retained only their futures, and verified that all eight queries remained reachable. Each synthetic statement deliberately held a 1 MiB payload, so the graph retained 8 MiB; this illustrates the mechanism and is not a measurement of a real driver's retained heap. Dropping the futures allowed all eight queries to be collected. This is heap retention, not proof that successfully closed database cursors remain open.

Use a static task type with a releasable owner/cleanup reference, cleared at the correct completion/cancellation boundary. Preserve the existing coordination for cancellation before execution and races with execution starting. Simply removing `done()` cleanup would reintroduce resource leaks. Validate success, failure, submission rejection, cancellation before/during execution, `closeAfterExecution(false)`, and retained completed futures. Confidence: high.

**F3. Bound intermediate mixed-ID batch-save runs by the requested batch size.**

Locations: [DaoImpl.java:3683](../src/main/java/com/landawn/abacus/jdbc/DaoImpl.java#L3683), through line 3698; the analogous `batchInsert` run is at [5290](../src/main/java/com/landawn/abacus/jdbc/DaoImpl.java#L5290), through line 5307.

When a `batchSave` input contains both default/generated IDs and explicit IDs, the implementation groups consecutive entities by their required INSERT shape. Each entire consecutive run is accumulated into an `ArrayList` before `executeBatchSave` splits it into database batches. Consequently the driver batch is bounded but the intermediate list is O(longest run). `clear()` also retains the backing array's high-water capacity until the whole operation ends. The initial ID-classification scans add more traversal.

With 10,001 input entities and batch size 100, the homogeneous path reached its first execution after consuming 100 entities; the mixed path reached it only after traversing all 10,001. Both ultimately submitted exactly 10,001 rows in 101 executions. The memory issue is extra reference storage and allocation, not duplication of every entity object; the input collection itself is already retained.

Flush a run when either its SQL shape changes or it reaches `batchSize`, preserving input order and the enclosing transaction. Where practical, reuse one statement for each of the two SQL shapes. Preserve generated-ID behavior and failure/rollback semantics, including `batchInsert`'s deferred ID assignment after commit. Its generated-ID results and deferred assignments intentionally remain O(N); the run buffer is additional storage. Validate long homogeneous prefixes followed by the other ID kind, alternating shapes, boundaries, generated-key mismatches, and batch failures. Confidence: high.

**F4. Use a projection-specific import path when no full-row callback is configured.**

Locations: [DataTransferUtil.java:820](../src/main/java/com/landawn/abacus/jdbc/DataTransferUtil.java#L820) and the shared loop at [1169](../src/main/java/com/landawn/abacus/jdbc/DataTransferUtil.java#L1169).

Selecting a small subset of Dataset columns changes the binding indices but still delegates to a loop that fetches every source column into a full-width scratch row. The default no-filter path supplies an always-true callback and receives the same treatment. Its work is O(rows x total columns) instead of O(rows x selected columns).

A real `RowDataset` with counting column lists demonstrated 5,000,000 source reads for 10,000 rows with 500 columns while only one column was bound, producing 10,000 bindings. The scratch array is reused, so this is mainly unnecessary source access/reference writes plus an O(total columns) array, not a per-row array leak. The 500:1 read ratio is not a claim of 500x end-to-end throughput.

Resolve selected indices once and bind directly from the Dataset in the no-custom-filter/no-custom-setter path. Preserve the full row for user callbacks that may inspect every column. Track whether a filter was actually supplied instead of trying to identify arbitrary always-true lambdas. Preserve selection order, duplicate selections, batching and cleanup. Confidence: high.

**F5. Separate reusable join metadata from unbounded table-key cardinality.**

Locations: [JoinInfo.java:1399](../src/main/java/com/landawn/abacus/jdbc/JoinInfo.java#L1399), [1455](../src/main/java/com/landawn/abacus/jdbc/JoinInfo.java#L1455), and [1610](../src/main/java/com/landawn/abacus/jdbc/JoinInfo.java#L1610).

Two process-wide maps strongly retain tuples containing DAO class, entity class and table name, along with metadata and by-type index maps. Neither has eviction or an owner lifecycle. Calling only the public JoinInfo APIs for 10,000 distinct table names produced 10,000 entries in each map, even though the entity had no joins. The probe did not create any DAO proxy. Tenant/partition table churn therefore grows retained state independently of the factory's documented permanent proxy caching.

For a fixed schema and class set, cardinality may be acceptably bounded. With dynamic metadata, split class/config-derived metadata from any necessary table-specific state, share empty results, and derive the type index from the same owned metadata. Evaluate bounded or lifecycle-owned caches. Preserve DAO-specific `allowNullOrDefaultJoinKeys` and thread-safe publication. A `ClassValue` can help class-owned metadata but must not retain unrelated disposable class loaders through its values. Fixing these two maps alone does not establish class-loader unloadability or bound applications also creating unlimited DAO proxies. Confidence: high; priority depends on cardinality.

**F6. Obtain prepared-statement metadata before executing a user-supplied query for code generation.**

Location: [JdbcCodeGenerationUtil.java:513](../src/main/java/com/landawn/abacus/jdbc/JdbcCodeGenerationUtil.java#L513), through line 516.

`generateEntityClassByQuery` executes the SELECT unconditionally, although the generator consumes column/origin/key metadata rather than rows. With a large result or expensive expression this can evaluate or buffer the entire result. The existing Javadoc recommends `WHERE 1 = 0`; that workaround is useful but is not required by the API.

On H2 2.5.252, a counting SQL function was evaluated 10,000 times to generate 383 characters of Java source. `PreparedStatement.getMetaData()` for the same SQL reported the required column with zero function evaluations. Actual transfer/buffering and metadata support vary by driver.

Refactor the generator core to accept `ResultSetMetaData` plus connection context and first try prepared-statement metadata. If unavailable until execution, use a supported limited fallback, retaining the documented zero-row-query workaround. `setMaxRows(1)` can limit returned rows but does not guarantee avoiding all server work for expensive sorts/aggregates. Do not mechanically append a WHERE clause to arbitrary SQL. Preserve column origins and primary-key resolution. Confidence: high for the tested path; validate additional supported drivers.

**F7. Avoid caching separate deep copies at every built-in forwarding layer.**

Locations: [DaoImpl.java:7459](../src/main/java/com/landawn/abacus/jdbc/DaoImpl.java#L7459), [7655](../src/main/java/com/landawn/abacus/jdbc/DaoImpl.java#L7655), [7727](../src/main/java/com/landawn/abacus/jdbc/DaoImpl.java#L7727), and the forwarding methods in [CrudReadOps.java:672](../src/main/java/com/landawn/abacus/jdbc/dao/CrudReadOps.java#L672).

With class-level `@CacheResult(enabled = true, serialization = JSON)`, inherited convenience overloads and the leaf read operation each receive a method-specific result-cache wrapper. A cold `batchGet(ids)` therefore enters several independently cached methods. Each returning layer calls `cloneFunc` and puts another copy under its own key, although only one leaf operation produced the data.

The probe requested 100 IDs from a `ReadOnlyCrudDao`. Its leaf `list` body ran once, but the cache contained four distinct list roots and four distinct copies of the first row: entries for `list`, `batchGet(ids, null, 200)`, `batchGet(ids, null)`, and `batchGet(ids)`. The subsequent warm call did not execute the leaf again. In this path, deep-copy serialization work and retained row graphs are multiplied by four and a bounded cache spends four entries on one external request. With `NONE` serialization, graphs may share objects, so the same deep-copy factor is not claimed. A single convenience call with multiple chunks can have a different amplification pattern.

Consider canonical cache ownership for known equivalent built-in overloads or an explicit policy to cache only an externally invoked operation. Preserve explicitly annotated method overrides, direct calls to inner methods, custom cache hooks, TTL/size policies, caller-mutation isolation and invalidation semantics; globally suppressing all nested cache calls would be too broad. As an immediate application-level option, narrow cache filters or explicitly disable caching on redundant wrappers after checking which entry points are used. Validate cold/warm alias calls and serialized graph counts. Confidence: high for the reproduced JSON path.

Several existing choices are sound and should survive tuning: transfer loops reuse scratch rows and clear batches; scalar and short-circuit query methods avoid unnecessary lists; lazy query streams have explicit cleanup; named-query bean metadata is resolved per batch; LOB materialization releases locators; DAO metadata and handler construction are generally cached; transaction scopes restore state and remove registry entries; scoped thread-local caches remove/restore their registrations in `finally`; and Spring application-context references are cleared on shutdown. Returned lists/Datasets and documented no-TTL map caches were not mislabeled as leaks. `SqlExecutor.java` is an archived placeholder: its historical implementation is commented out.

Implementation should start with F1 and F2, plus F7 for class-level serialized caching, then the applicable batch/projection paths. Metadata-heavy applications should prioritize F5/F6. Configure async capacity and reuse DAO configurations immediately where workloads demand it. Use representative JFR allocation/retained-heap measurements and integration throughput tests to decide which optional changes justify their complexity; preserve behavior before pursuing timing improvements.
