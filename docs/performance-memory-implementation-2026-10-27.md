# Performance and memory improvements — 2026-10-27

Implements F1, F3, F5, F6, and the connection-reuse portion of F7 from the [review](performance-memory-review-2026-10-27.md). F2 receives documentation on connection capacity. F4 and F8 remain deferred. No new pagination, cache eviction, retry policy, or public API is introduced.

| Finding | Change | Scope and compatibility |
|---|---|---|
| F1: premature result advancement | `JdbcUtil.iterateAllResultSets` advances on the next demand, after delivering the current result. | Still-open results retain KEEP semantics where supported; explicitly unsupported KEEP falls back to CLOSE. Already-closed results advance with CLOSE, avoiding registration in the driver's open-result tracking. Failures after delivery leave result ownership with the caller. |
| F1: streaming close ordering | Connection metadata must identify `MySQL Connector/J`, and the statement must use `Integer.MIN_VALUE` fetch size, forward-only, read-only results, before pre-close draining is enabled. | Identification works through JDBC pool wrappers without linking optional driver classes. Other/unknown drivers retain ordinary close behavior. SQLExceptions during optional identification are logged at debug level and retain ordinary close behavior, so unavailable metadata does not prevent result delivery. Connector/J notifies its statement before its normal close-time drain discovers later results; draining first preserves trailing results after partial extraction. Public stream Javadoc explains the reads required on early close. Buffered results are not walked solely to close them. |
| F2: nested connection acquisition | Documented all three enrichment-stream overloads and their unchecked inheritance. | Outside a bound transaction, child queries need additional available capacity. Within one, they reuse the parent connection, so an active streaming cursor may prevent another statement; increasing the pool cannot resolve that restriction. Driver-supported buffering, materializing and closing parent results, explicit paging, or a server-side join are alternatives. |
| F3: retained scratch rows | Nine callback/finisher/map factories clear reusable object arrays in `finally`, including partially filled arrays on failures. | Arrays are reused, copied result values survive, and disposable-array-returning mapper APIs retain their existing view semantics. Clearing adds a linear reference-clearing pass per row. |
| F5: repeated name analysis | Prepare-batch statement/call and ordinary/large batch-update paths analyze the immutable parameter-name layout once per batch. | A resolved null layout means no duplicates. Row values, types, bean getters, and replayable stream buffers remain per-row. Mixed bean/map/positional rows retain their binding semantics. |
| F6: metadata fallback | Apply `setMaxRows(1)` immediately before executing the metadata fallback query. | Prepared metadata fast paths do not receive a cap. Explicit unsupported-feature/unimplemented-method cases, including plain `SQLException` with SQLState class `0A`, continue without the cap. Unrelated or unclassified failures propagate. One row remains available for dynamic column typing; the cap does not guarantee bounded server scans or sorting. |
| F7: lock connection churn | Reuse the cleanup connection for INSERT within a normal acquisition attempt. | It remains independently owned and auto-commit, and is released before retry sleep or lock publication. Failed cleanup discards its connection and preserves the fresh-connection insertion attempt. Expiry/stale-row rules, ownership codes, retry intervals, and interruption behavior remain unchanged. |

The F7 change reduces normal connection acquisition/close cycles from two to one per attempt. There are still two statements and a duplicate-key exception on live contention. Replacing the cleanup DELETE with an expired-row UPDATE followed by INSERT on zero rows would not eliminate that exception.

A warmed JDK 21 allocation probe exercised the real 64-parameter `prepareBatchStmt` map-binding path against a no-op JDBC statement: three runs of 10,000 rows each measured **3,192.1 B/row before** and **570.7 B/row after**, with identical figures across runs. Each batch contains 1,000 rows. The approximately 2,621 B/row reduction reflects amortized name analysis; per-row value/type arrays remain. This measures Java allocation, not production throughput or database latency. The maintained [probe and usage instructions](../tools/benchmarks/README.md) survive Maven clean. Functional tests additionally cover 64 distinct names and a reversed repeated-name layout, with different row values across all four batch routes; these tests verify binding behavior, not the allocation improvement.

Regression coverage includes the pinned Connector/J's actual advance, close, and close-notification methods with simulated row sources; partial/full and streaming/buffered results; unsupported KEEP and error ownership; scratch-buffer retention on success/failure; mixed batch parameter shapes and repeated streams; real H2 metadata evaluation; and lock resource counts, failed cleanup, interruption, and stale ownership. The Connector/J tests do not require or represent a live MySQL server run.

Single-result extraction follow-up (2026-10-28): both `CallableQuery.queryAndGetOutParameters` extractor overloads now obtain the first result through the existing result iterator and retain that iterator for failure cleanup. This prevents an ordinary early close from losing undiscovered Connector/J results or swallowing a procedure error. Extraction still discards remaining results before reading OUT values, and failures retain their original exception with cleanup failures suppressed. The no-argument Dataset overload delegates to this path. Fetch-direction initialization and restoration are preserved through a shared helper; ordinary `executeQuery()` wrapping is unchanged. Connector/J's restriction against streaming with registered OUT parameters remains: streaming tests exercise these APIs without OUT registrations. Earlier streamed delegates are not newly retained or tracked for deferred closure.

Live MySQL regression cases cover both extractor overloads, partial reads, reuse of the same query and connection, procedure errors after the first or a later result, and extractor failures with or without a subsequent procedure error. These cases require the existing explicitly enabled MySQL test configuration.

The single-result paths also preserve their prior recovery from a false result-set claim: when execution claims a result but returns `null`, they advance even if the update count is `-1`. An iterator option enables this only for the two affected overloads; existing iterator callers retain their termination behavior. Regression coverage checks both recovery paths and verifies that buffered OUT values are read only after remaining results are discarded.
